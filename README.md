# medcode-eval

A small, coder-verified test set that measures how large language models
handle ICD-10-CM diagnosis coding, together with a rules checker that reads
the current code-set files and is itself one of the tested conditions.

- Version: 0.1.0
- Code set: ICD-10-CM FY2027, October 1, 2026 release. Everything here is
  pinned to that release. A later release, including an April 1, 2027
  update, is a different code set.
- Author: mdzAI14

Medical coding turns a clinical note into the diagnosis codes a claim
reports. The code set changes every year, and the rules for choosing and
ordering codes are detailed. This project asks three plain questions about
a model, and answers each one with files anyone can re-check.

## What it measures

1. **Does the model know the code set, including what changed this year?**
   Part A asks about single codes: which description belongs to a code,
   which code belongs to a description, and whether a code is billable, a
   header, or not in the code set.
2. **Does the model apply the rules on cases built around known traps?**
   Part B gives the model a short clinical note and asks for the diagnosis
   codes in reporting order. Each of its 25 cases is built around one trap:
   laterality, a 7th character, an Excludes1 note, a combination code, or
   sequencing.
3. **Does a rules checker that reads the current files improve the
   answers?** The checker looks at the model's codes, and the model sees
   its findings once and may revise once.

## What it does not measure

It does not measure production coding. The notes are short and synthetic,
only diagnosis codes are scored, five specialties are covered, Part B has
25 cases, and one coder verified the gold codes. Read the results as a
probe of specific skills, not as an accuracy rate for real charts. The
Limitations section lists the rest.

## What is in the test set

**Part A, code-set knowledge.** Probes are generated by code from the
reference files under `refdata/`, with no human or model input, and each
probe's answer comes from those files.

- `data/part_a/probes_lite.jsonl`: 151 probes on codes that are not new in
  FY2027 (50 code-to-description, 50 description-to-code, 51 status).
- `data/part_a/probes_changes.jsonl`: 462 probes on every code that
  changed in FY2027: new billable codes, new headers, billable codes that
  became headers, and removed codes.
- `data/part_a/probes_full.jsonl`: 1,501 probes of the same kinds as the
  lite set. No reported run uses it yet.

**Part B, trap cases.** 25 cases, five in each of orthopedics,
ophthalmology, gastroenterology, ENT and emergency medicine, with every
specialty meeting every trap once. Each case is three files with one id:
a fact list (`data/specs/`), the note the model reads (`data/cases/`), and
the gold codes with their guideline citations (`data/gold/`). The model
sees the note text and nothing else. `docs/part_b_schema.md` describes the
files, and the Datasheet section below says how they were made.

**The checker.** `python -m medcode_eval.checker CODE ...` checks a list
of codes against the FY2027 order file and tabular file. It reports
errors (a code that is not in the code set, a header that is not billable,
a manifestation code listed first) and review findings (a pair of codes
with an Excludes1 note between them, a pair in the wrong order for a "code
first" note). It has no rule for Excludes2, "use additional code" or "code
also" notes. It cannot tell whether a valid code is the right one.

## Results

All figures in this section are in `results/RESULTS.md`, which is rebuilt
from the stored model replies by `python -m medcode_eval.results`. The
section letters in brackets point there.

### Models and settings

| Model | How it was run | Settings |
|---|---|---|
| Claude Opus 5.5 (`claude-opus-5-5`) | provider API | effort medium; no temperature set; its reasoning cannot be turned off |
| qwen3:4b | local, Ollama, CPU only | reasoning off (`/no_think`); temperature 0; fixed seed |

Opus is the frontier model. qwen3:4b is a floor: the largest model the
author's machine could run. Every run was made once, on 2026-11-11 or
2026-11-16 [S0].

### Part A: does the model know the code set?

Correct answers out of the probes asked [S1, S2]:

| Probes | n | Claude Opus 5.5 | qwen3:4b |
|---|---|---|---|
| **Codes that are not new in FY2027 (lite set)** | 151 | 147 (0.97) | 41 (0.27) |
| code to description | 50 | 50 | 21 |
| description to code | 50 | 50 | 0 |
| status | 51 | 47 | 20 |
| **Codes that changed in FY2027 (changes set)** | 462 | 100 (0.22) | 28 (0.06) |
| description to code, new billable codes | 188 | 43 | 0 |
| status, all changes | 274 | 57 | 28 |
| status, new billable code | 190 | 49 | 5 |
| status, new header | 48 | 6 | 2 |
| status, billable code that became a header | 15 | 1 | 0 |
| status, removed code | 21 | 1 | 21 |

- Opus is nearly perfect on codes that did not change and unreliable on
  codes that did. It called 140 of the 190 new billable codes "not a
  code". Its knowledge of the code set stops before FY2027.
- Asked for a new code by its description, Opus gave the right code 43
  times, a wrong code 71 times, and no single code 74 times. Of those 74
  replies, 71 open by saying it cannot confirm the answer (a pattern
  count, not a reading) [S2].
- qwen3:4b's 21 of 21 on removed codes is not knowledge: it answered "not
  a code" to 263 of the 274 status probes on the changes set.

Run alone over the stored answers, the checker marks 60 of the 71 wrong
codes Opus gave for new descriptions as errors: 50 are not in the code set
and 10 are headers. The other 11 are valid codes that are the wrong ones,
which the checker cannot see [S3].

### Part B: does the model apply the rules?

25 cases, 43 required codes [S5, S6]:

| | Opus, plain | Opus, with checker: first answer | Opus, with checker: final answer | qwen3:4b, plain | qwen3:4b, with checker: final answer |
|---|---|---|---|---|---|
| Exact match with the gold codes | 21 | 23 | 23 | 0 | 0 |
| First-listed code right | 24 | 25 | 25 | 0 | 0 |
| Required codes found, of 43 | 40 | 42 | 42 | 1 | 1 |
| Extra codes | 5 | 3 | 3 | 127 | 46 |
| Codes the checker marks as errors | 3 | 1 | 0 | 116 | 26 |
| Answers that could not be read | 0 | 0 | 0 | 1 | 2 |

Every group by trap or by specialty has 5 cases, too few to read on its
own; `results/RESULTS.md` flags those rows.

Where Opus missed [S6]:

- **b-gi-001, in both runs: the one labelled trap it fell for.** It
  reported K29.01 with K25.4 against the Excludes1 notes between them,
  and added B96.81 from a lab result the provider had not linked. Shown
  the checker's two review findings, it kept its answer.
- **b-ophtho-004, in both runs: a code from an older code set.** It gave
  H13, which is not in the FY2027 code set, where the gold code is
  H10.823.
- **b-ent-004 and b-ortho-002, in the plain run only: codes the checker
  rejects.** It gave V18.49XD and S82.611D. In the other run its first
  answers on both cases were right.

So apart from one trap, every miss was about what is in the current code
set, the same gap Part A shows.

qwen3:4b found 1 of the 43 required codes and matched no case. On one
case it listed 81 codes that are not in the code set.

### Does the checker help?

**On the Part B cases, not measurably.** The effect is read inside the
with-checker run, first answer against final answer [S5, S7].

- Opus: findings went back on 2 of 25 cases and one answer changed. On
  b-ophtho-004 the checker flagged H13; Opus replaced it with H10.403,
  which is in the code set and is not the gold code. Exact matches stayed
  at 23.
- The difference between 21 (plain run) and 23 (with-checker run) is not
  a checker effect. It comes from first answers, before any finding was
  sent: two runs of the same prompt gave different codes on two cases,
  and the same codes in a different order on a third [S7].
- qwen3:4b: no answer became correct. One second turn hit the runner's
  time limit, so that case has no final answer; the drops in extra codes
  (127 to 46) and in error findings (116 to 26) are mostly that lost
  answer. Leaving the case out, error findings fell from 35 to 26 across
  9 changed answers [S7].

**On new codes, yes, with a cost.** The same test was run on the 188
description-to-code probes for new FY2027 codes. The 60 stored Opus
answers that were not in the code set, or were headers, each got one
second turn with the checker's finding [S4].

| 188 probes, Claude Opus 5.5 | First answer | After the checker turn |
|---|---|---|
| Correct | 43 | 65 |
| Wrong code | 71 | 33 |
| No single code read | 74 | 90 |

| Finding sent | Sent | Became correct | Valid but wrong code | Still an error | No single code read |
|---|---|---|---|---|---|
| Header, not billable | 10 | 8 | 1 | 0 | 1 |
| Not in the code set | 50 | 14 | 16 | 5 | 15 |
| Total | 60 | 22 | 17 | 5 | 16 |

- The checker helps where its finding carries structure. A header finding
  lists the codes under the header, and Opus picked one of them 9 times
  out of 10, correctly 8 times.
- It does not help where the model has to name a code it has never seen.
  Eight final answers fell back to the "longest stored prefix" the
  finding names, and none was right.
- The cost: 17 flagged answers became a different code that is valid and
  wrong. Wrong codes the checker cannot see rose from 11 to 28.
- The answer reader is strict: a reply that hedges after its code can
  count as "no single code read". Under a lenient reading, defined after
  the results were seen, the two counts become 44 and 66, so the gain of
  22 stands [S4].

The four Opus runs that have a usage summary cost 6.20 USD together at 4
and 20 USD per million input and output tokens [S8].

## Reproduce

Python 3.12, standard library only; there is nothing to install. From the
repository root:

    python3 -m venv venv
    venv/bin/python -m unittest discover -s tests -t .
    venv/bin/python -m medcode_eval.part_b.validate
    venv/bin/python -m medcode_eval.results --check

The last command re-reads every stored model reply with the package's own
readers, re-scores the stored answers against `data/`, and compares the
outcome with `results/RESULTS.md`. It exits 0 only if everything matches.
`results/README.md` describes the stored files.

To try the checker on a pair of codes:

    venv/bin/python -m medcode_eval.checker K25.4 K29.01

## Run it on another model

A local model served by Ollama, Part B, both conditions:

    venv/bin/python -m medcode_eval.run.runner --part b --condition plain --run-id MY-RUN-plain --backend ollama --model MODEL
    venv/bin/python -m medcode_eval.run.runner --part b --condition with_checker --run-id MY-RUN-checker --backend ollama --model MODEL
    venv/bin/python -m medcode_eval.part_b.score --run-id MY-RUN-plain

Part A, lite set:

    venv/bin/python -m medcode_eval.run.runner --part a --probes data/part_a/probes_lite.jsonl --run-id MY-RUN-lite --backend ollama --model MODEL
    venv/bin/python -m medcode_eval.part_a.score --probes data/part_a/probes_lite.jsonl --responses runs/part_a/MY-RUN-lite/responses.jsonl --out-json runs/part_a/MY-RUN-lite/score.json --out-md runs/part_a/MY-RUN-lite/score.md

Run folders are written under `runs/`, which git ignores. The `remote`
backend speaks one provider's Messages API. It reads the key from a
variable in a `.env` file at the repository root, and it will not start
without prices, a spending cap and a ledger file
(`python -m medcode_eval.run.runner --help` lists the options); every
request is checked against the cap before it is sent.

The prompt files under `medcode_eval/run/prompts/` were fixed before the
reported runs and should not be changed when comparing with them.

## Datasheet for Part B

**Source.** Every case is invented. No case comes from, or is recalled
from, a real patient record.

**Specs.** A spec is a flat list of clinical facts with no codes and no
trap label. The author wrote 15 of the 25 and an AI assistant (Claude
Fable 5.2, in a design chat) drafted 10 at his instruction: b-gi-003,
four of the five cases numbered 004, and all five numbered 005. The
author approved every spec; the specs he wrote had AI help with
formatting. Scenarios were chosen so that the trap rests on a note that
exists in the FY2027 files.

**Notes.** The note the model reads was drafted from the spec by Claude
Fable 5.2. Each case file records this in its `origin` and `drafter`
fields.

**Gold codes.** The codes were drafted with commercial coding software
that has AI assistance. The explanations and formatting were drafted with
a Claude model. The wording of the citations was drafted by a Claude
model from the author's rulings and checked against the text of the
FY2027 Official Guidelines tracked under `refdata/`. The author, a
medical coder, verified every code and citation; where he could not
settle a code from a guideline or a code-book note, the code became
optional and did not default to the AI's draft. Each gold file records
this in its `method` and `method_detail` fields. Describe this test set
as coder-verified, not coder-authored.

**Optional codes.** A gold file may list codes the author judges
defensible either way for that case. The scorer neither requires nor
penalizes them. Eight cases carry 12 optional codes in all.

**Evaluated model and drafting models.** The notes and part of the gold
text were drafted by Claude models, and the frontier model evaluated is
also a Claude model (Opus 5.5). No model was evaluated on gold it
drafted, but the shared family may favor Opus on wording and style.

**Review runs, and the gold changes that followed them.** While the cases
were being written, each batch was run through Opus once in each
condition as a second look at its gold. Those runs are not reported
results; their replies are stored under `results/review/`. Four gold
files changed after a run of the evaluated model:

- **b-ent-001.** The optional-code field was added on 2026-11-11, after
  the first pilot runs. Its first entry, B95.0 on this case, is a code
  Opus had given in one of those runs.
- **b-ortho-002.** The required fall code was changed from W19.XXXD to
  W18.30XD on 2026-11-15, after Opus gave the same-level code in both
  review runs.
- **b-ortho-003.** Four external cause codes were changed from left off
  to optional on 2026-11-15, after Opus added them in a review run.
- **b-ed-001.** Y99.8 was changed from left off to optional on
  2026-11-16, when the citations were checked against the guidelines
  text. Opus had given it in both pilot runs, and gave it again in both
  reported runs [S6]. Had the code stayed left off, this case would not
  be an exact match in either reported run.

All gold was settled before the reported Part B runs were made, and no
gold file has changed since.

**The cases.** Each id is `b-<specialty>-<number>`.

| Number | ortho | ophtho | gi | ent | ed |
|---|---|---|---|---|---|
| 001 | laterality | combination | excludes1 | sequencing | seventh_character |
| 002 | seventh_character | laterality | combination | excludes1 | sequencing |
| 003 | excludes1 | seventh_character | sequencing | combination | laterality |
| 004 | combination | sequencing | laterality | seventh_character | excludes1 |
| 005 | sequencing | excludes1 | seventh_character | laterality | combination |

## Limitations

- **One verifier.** A single coder verified the gold, with no second
  coder. A blind re-check of a sample of cases by the same coder is
  planned and not yet done.
- **AI-drafted gold.** The codes, explanations and citations began as AI
  drafts. Verification catches errors; it does not make the gold
  independent of those drafts.
- **Synthetic, short notes.** The notes state every fact a code depends
  on. Real charts are longer, messier and often incomplete.
- **Small.** 25 cases, 5 per trap and 5 per specialty. One case is 4
  points of exact match.
- **Diagnosis codes only**, in five specialties. No procedure codes, no
  payer rules, no code sets other than ICD-10-CM.
- **Each run was made once.** Opus gives different answers to the same
  prompt on some cases, so a difference of one or two cases between runs
  is within its run-to-run variation.
- **Two models.** One frontier model and one small local model. The
  results say nothing about other models.
- **Part A tests recall of code and description pairs**, not coding. The
  changes set is hard for any model trained before the FY2027 files
  existed; that is what it is for.
- **The checker is a first version.** It covers five rules and reads
  parenthesised code references in tabular notes only.
- **Strict answer reading.** A reply that does not put a single code or a
  JSON list where the prompt asks for it counts as invalid, even when a
  person could read an answer in it.

## Repository layout

- `medcode_eval/`: the package: reference-file loaders, the checker, the
  Part A generator and scorer, the Part B validator and scorer, the
  runner, and the results module.
- `data/`: the test items. `results/`: stored run outputs and
  `RESULTS.md`. `refdata/`: the unmodified public FY2027 reference
  files, listed with their sources in `refdata/MANIFEST.md`.
- `tests/`, `docs/`, `templates/`, `scripts/`.

This project is a companion to the author's MedCode project and is
independent of it.
